CRM-BaseBot 接手手册

渠道佣金 CRM：飞书多维表格 + 机器人。这份是**唯一入口文档** —— 人看它、AI agent 也看它。

目标：把整套系统搬进你自己的飞书账号，并让它跑起来 预计 30–60 分钟（大部分时间在飞书后台点几下 + 等发版审批）
给 AI agent 的一句话：仓库里是一套已经在原主人账号跑通的飞书 CRM（每天取销售明细 → 只导新加坡站的新增交易日 → 看板按 UID 自动算每笔佣金 → 机器人让销售自己登记渠道/客户/查佣金）。你的任务是把这套系统在委托人自己的飞书账号里建起来。按本文顺序执行即可，不要重新设计；需要人在浏览器点的三下在 第 2 步，其余你都能做。机器可读的同一份内容在 HANDOFF.md。

1 · 环境与账号要求

机器（跑命令的那台）

要求说明 · 怎么满足
macOS / Linux（Windows 也能跑，见备注） 机器人、导入、迁移都是纯 Python，跨平台。只有「定时任务」脚本是 macOS 的 launchd；Linux 用 cron、Windows 用任务计划程序替代（见第 7 步）。
uv（唯一需要你装的工具） curl -LsSf https://astral.sh/uv/install.sh | sh
它会把 Python 和依赖都装好 —— 不需要你先装 Python（项目要求 ≥3.12，uv 会自己取 3.13）。
git clone 仓库用。git --version 有输出即可。
网络 必须：open.feishu.cn（或国际版 open.larksuite.com）、github.com。
可选：graph.microsoft.com（只有第 7 步的「邮件自动取数」需要）。
磁盘很小：代码 + 依赖 < 300 MB；导出的 xlsx 每份 1–3 MB。

飞书账号（这一步最容易踩坑）

必须是「企业/团队」账号，个人版不行。个人版没有管理后台，而「开权限」「发版」都需要管理员在后台点「通过」—— 所以个人版里应用永远发不出去（拿到 App ID 也没用，权限和机器人能力都不生效）。
自建免费的企业就行（免费基础版够用，不需要营业执照）。用 +86 手机号建飞书企业；只有港号就走国际版 Lark。
项要求
权限能在组织里创建自建应用；改权限/发版需要管理员审批（一次即可，建议一次开齐）
应用权限清单 bitable:app（读写多维表格 —— 必须）
im:message.p2p_msg:readonly + im:message:send_as_bot（机器人收/发消息 —— 第 7 步要用）
contact:user.base:readonly（可选，当前代码没调用，一起申请省得二次审批）
注意：接收消息用的不是 im:message，而是 im:message.p2p_msg:readonly（官方事件文档里才写得对）。详见 docs/LARK_APP_SETUP.md「第 4 步」。
事件订阅im.message.receive_v1（接收消息）+ 卡片回调 card.action.trigger，用长连接方式（不需要公网地址）
一个空 Base不需要手工建 —— 第 4 步的方案 A 会让应用自己建一个（省掉「把应用加成协作者」这个 403 坑）

可选（只有「每天自动取数」需要）

Microsoft Entra 应用授予 Mail.Read（应用程序权限）并限定到收销售明细的那个邮箱。没有也能用：手工把 xlsx 放进 attachments/ 再跑导入。

2 · 建应用（人在浏览器点 4 下）

  1. 打开 open.feishu.cn/app → 创建企业自建应用 → 名字建议 CRM-BaseBot
  2. 进应用 → 左侧 「凭证与基础信息」 → 复制 App ID / App Secret
  3. 左侧 「权限管理」 → 按上表把权限一次开齐（至少 bitable:app）
  4. 左侧 「版本管理与发布」 → 创建版本 → 申请发布（管理员批准）
第 3、4 步漏任何一个，后面所有接口都会 403，而报错信息完全看不出是这个原因 —— 这是整条路上最容易卡死的地方。确认「版本状态 = 已发布」再往下走。

3 · 准备仓库与配置

git clone <仓库地址> CRM-BaseBot && cd CRM-BaseBot
uv sync                                  # 装依赖（会自动准备 Python）
cp .env.target.example .env.target       # 模板里每一项都写了「去哪拿」

把 App ID / App Secret 填进 .env.target 的第 21、22 行（不要引号、不要空格）。LARK_BASE_APP_TOKEN 留空 —— 用下面的 --create-base 让应用自己建 Base。

uv run python scripts/migrate_base.py --target-env .env.target --dry-run

这一步只读配置、不联网。看到「迁移没法继续：…还没填目标账号的应用凭证」就回去填；看到「新建 Base「…」（预演，没有真的建）」就说明配置对了。

4 · 把数据搬过来（三条路，选一条）

数据不在 git 里。仓库里只有代码和文档（约 97 个文件、零条业务数据）；真正的资产是飞书 Base 里的内容：看板约 1,650 行、渠道约 101 条、客户约 113 条、销售名册 4 人。这些只能靠下面三条路之一搬，不会随 git pull 过来。

方案 A · 凭证迁移（推荐）

委托人给你源端 .env，或你把 .env.target 给原主人让他跑。一条命令搬完结构 + 数据。

uv run python scripts/migrate_base.py \
  --target-env .env.target \
  --create-base "CRM 佣金看板" --apply

幂等检查：每张表都会打印「源 N 条 → 目标 N 条」，全 ✅ 才算成功。

方案 C · 只交接文件（不换凭证）

原主人给你一个 zip（渠道客户.xlsx + 看板.xlsx + 导入说明）。是 xlsx，不要 CSV：18–19 位的客户 UID 经 CSV/Excel 转手会被抹掉末尾几位 —— 那种 UID 之后永远算不出佣金，而且不报错。

cp .env.target.example .env   # 填 App ID/Secret + Base token
# 两个 xlsx 放到仓库根目录，一条命令导完：
uv run python scripts/import_handover.py --dir . --dry-run
uv run python scripts/import_handover.py --dir . --apply

这条命令自己会：建 6 张表（含公式列）+ table_id 自动写进 .env → 导渠道/客户 → 导看板 → 名册按姓名补齐。数据只导一次（没有 UID 的客户重复导会堆重复行）。

（方案 B：原主人把源端 .env 直接给你，你这边一条命令跑完 —— 与 A 相同，只是跑在哪台机器的区别。）

5 · 搬完立刻自检

cp .env.target .env                 # 之后所有脚本都指向委托人的 Base（.env 在 .gitignore 里）
uv run python scripts/inspect_base.py          # 核对 6 张表、行数、字段
uv run python scripts/verify_commission.py     # 期望结论：逐行一致，没有差异

verify_commission.py 不看 Base 的公式列，而是自己按「用户ID → 客户表 → 所属渠道 → 分佣比例」复算一遍再逐行对比。它报「逐行一致」就等于同时证明了三件事：关联没搬错、公式生效、钱算得对。

6 · 还需要人做的两件（open_id）

前置：新的机器人得先跑起来（见第 7 节）。open_id 是应用签发的 —— 委托人这边是一个全新的应用、全新的 bot，在它上线之前，销售发的消息没有任何东西接收，也就拿不到任何 open_id。
正确顺序：建应用 / 开权限 / 发版（第 2 节）→ 把机器人跑起来（第 7 节）→ 收 open_id（本节）→ 回填归属（本节）。原主人那台机器上的机器人服务的是原账号，与这里无关。
为什么必须人做：open_id（飞书里「这个人是谁」的 ID）是按应用签发的 —— 原账号的 open_id 在委托人的账号里是无效值，所以名册和归属都没搬。搬完机器人里「我的渠道」是空的，这不是数据丢失，是归属还没认领。 
# ① 让要用的每位销售各给机器人发一条消息；服务端日志会出现他的 open_id：
#    WARNING crm_basebot.bot.auth: 未登记的 open_id 尝试操作: ou_xxxx
uv run python scripts/set_sales_open_id.py --name "某人" --open-id ou_xxxx --apply
uv run python scripts/set_sales_open_id.py --list          # 核对：OpenID 那列有值了

# ② 名册填好之后，按「负责销售」姓名把渠道/客户的归属接上：
uv run python scripts/backfill_owners.py --dry-run         # 先看会回填多少条
uv run python scripts/backfill_owners.py --apply

① 之前，销售在机器人里点「我的渠道」是空的、登记客户时渠道下拉也是空的。② 之后即可正常使用。

7 · 让机器人上线 / 每天自动取数

机器人（长连接，不需要公网地址）：

uv run python -m crm_basebot.app            # 前台跑；常驻见 docs/BOT.md

应用侧要开启机器人能力、订阅 im.message.receive_v1 + 卡片回调，照 docs/LARK_APP_SETUP.md 清单配 —— 和权限一样，改完要重新发版。

每天自动取数（需要第 1 步末尾那 4 个 Microsoft Graph 键）：

./scripts/run-daily-import.sh --dry-run     # 先验：应该能取到今天那份附件并算出增量
./scripts/install-daily-import-launchd.sh   # macOS：每天 10:45 / 16:00（Linux 用 cron 替代）

8 · 出问题对照表

现象多半是怎么办
接口 403 / permission denied权限没开、没发版，或（自己建 Base 时）应用没被加成协作者回第 2 步的 3、4；自己建的 Base 另加「分享 → 应用 → 可编辑」
没有权限访问该多维表格LARK_BASE_APP_TOKEN 填的是另一个账号的 Base核对 Base URL 里的 token
看板有数据但佣金列全空公式列没建出来 / 客户关联没挂上uv run python scripts/sync_base.py --apply（它会做公式自检并说明原因）
行数对不上（源 N → 目标 M<N）个别记录含目标端不存在的字段/非法值，被接口整批拒了看迁移报告里带 ⚠️ 的行，把那张表的 dry-run 输出发给原主人
机器人对谁都回「你还没有被登记为销售」名册 OpenID 还空着第 6 步 ①
机器人里「我的渠道」是空的归属还没回填第 6 步 ②
机器人断线 / 收不到消息网络或 DNS（长连接不补发断线期间的消息）看 docs/BOT.md 的「断线时间线」判读方式
uv 命令找不到没装或没重开终端curl -LsSf https://astral.sh/uv/install.sh | sh，然后新开一个终端

9 · 设计要点（免得好心改坏）

  • 钱只在 Base 里算。看板的 分佣比例/本笔佣金/月份 是公式列，Python 不参与算钱；verify_commission.py 只是复算校验。
  • 只导新加坡站。站点列是「新加坡站」的行才进看板，其它站点解析完就丢（既定口径）。
  • 关联一律按业务键。客户 ↔ 渠道用「渠道编号」，看板 → 客户用「客户UID」。不要改回按姓名匹配（大小写、last/first 颠倒会出错，原主人踩过）。
  • 每天的导入是增量。只写看板还没有的交易日、整天替换；--max-days（默认 5）是防呆闸门。
  • 细一点的背景：docs/PIPELINE.md（每日管线）、docs/BOT.md（机器人现状与缺口）、docs/MIGRATION.md（迁移细节）、docs/SCHEMA.md（表结构）、docs/DASHBOARD.md（仪表盘）。
