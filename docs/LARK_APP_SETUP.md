# 阶段 A：自建免费组织，零审批跑通

这份文档只服务一个目的：让你在**不惊动公司 IT** 的前提下，把整套东西在本地跑通。跑通之后再带着能演示的成品去走一次审批，见 [IT_APPROVAL.md](IT_APPROVAL.md)。

## 为什么可以绕过审批

飞书官方文档在[企业自建应用开发流程](https://open.feishu.cn/document/develop-process/self-built-application-development-process)里写得很明确：

> 在应用测试阶段，开发者可以自行创建一个新企业，在新企业中创建应用、添加权限，**实现权限免审**。

你在自己创建的组织里就是管理员，加权限不需要任何人点头。等本地全跑通了，公司那边只需要审批**一次**。

关于免费版的 API 额度，见文末[附录：免费版的 API 调用额度](#附录免费版的-api-调用额度)。结论是开发测试碰不到上限。

---

## 第 1 步：建一个自己的飞书组织

这一步最容易一开始就走错，而且错了要到第 5 步才会暴露出来，所以先把「租户」这件事讲清楚。

### 先搞明白：飞书有三种「版本」，只有一种能开发

飞书账号背后一定挂着一个**租户**（tenant），租户分三类：

| 租户类型 | 怎么来的 | 能不能开发自建应用 |
| --- | --- | --- |
| **飞书个人版** | 用手机号注册后没有创建也没有加入任何企业，系统给你的默认身份 | **不能**，见下文 |
| **团队 / 企业（基础免费版）** | 自己点「创建企业」建出来的，免费，不需要营业执照 | **能**，且你自己就是管理员，权限和发布全部免审 |
| 公司的正式租户 | 公司 IT 建的，你是被邀请进去的成员 | 能建应用，但每次改权限都要 IT 审批 |

阶段 A 要的是中间那一栏。

### 为什么个人版是死路

飞书官方《[用户身份概述](https://open.feishu.cn/document/home/user-identity-introduction/introduction)》里有一句话直接判了死刑：

> 刚完成注册的飞书用户属于个人身份，你可以在飞书 App 上看到 `飞书个人版` 的标识。**飞书个人版无法访问企业的管理后台进行组织管理。**

这一句为什么致命，要串起另外两条官方规则才看得出来：

1. 《企业自建应用开发流程》：「在飞书开放平台上开发应用前，你必须先成为飞书的**企业用户**。你可以通过创建企业或加入企业方式成为飞书企业用户。」
2. 《[发布与审核自建应用](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review)》：「当应用的**基本信息、权限范围、应用功能和事件订阅**等信息发生变更时，都需要发布新的应用版本，并且通过**企业管理员**的审核后才能生效。」

连起来就是：本项目需要的每一样东西 —— 开启机器人能力、申请 `bitable:app` 等权限、订阅 `im.message.receive_v1` 和 `card.action.trigger` —— 全都属于「必须发版本、必须管理员审核才生效」的那一类。而审核动作发生在**管理后台**（www.feishu.cn/admin），个人版进不去这个后台，也就没有任何人能点那个「通过」。

所以你在开发者后台点「创建应用」时看到的那句：

> This app is available only within 飞书个人版, and can be published upon the approval of the organization administrator.

翻译过来是「这个应用只能在『飞书个人版』这个租户内使用，需要组织管理员审批后才能发布」。这里的 `飞书个人版` 是你当前租户的名字，不是产品宣传语。而个人版这个租户根本不存在管理员这个角色，所以那句「等管理员审批」在个人版语境下等于「永远不会有人来审批」。

补充一条旁证：官方《[应用概述](https://open.feishu.cn/document/platform-overveiw/overview)》对比两类应用的「使用人员」时，商店应用写的是「企业内部人员、**飞书个人版用户**」，企业自建应用只写「企业内部人员」。个人版被明确排除在自建应用之外。

> 说明一下这里哪些是文档写死的、哪些是推断。「个人版没有管理后台」「自建应用改权限必须管理员审核」「开发前必须先成为企业用户」这三条是官方原文。「所以个人版的应用永远发不出去」是这三条推出来的结论 —— 官方没有一句话直白写「个人版不能建自建应用」，开发者后台甚至可能让你把应用对象建出来、拿到 App ID。别被这个假象骗了：能拿到 App ID 不等于能用，机器人能力和权限一样不生效。

### 怎么确认自己现在在哪种租户

打开飞书桌面端，点左上角自己的头像，看名字下面那一行：

- 显示 `飞书个人版` —— 你在个人版，必须往下走建一个团队
- 显示某个公司/团队名字，后面跟着「已认证」或「未认证」 —— 你在一个企业租户里，可以直接用
- 头像菜单里有「管理后台」这个入口 —— 说明你是这个租户的管理员，这正是我们要的状态

### 建一个自己的团队（已有飞书账号的情况）

**不需要换手机号，也不需要注销现有账号。** 飞书允许同一个手机号下挂多个账号，每个账号属于不同租户，在客户端左侧栏一键切换。官方《[创建企业](https://www.feishu.cn/hc/zh-CN/articles/360043741453-创建企业)》里「已有飞书账号」一节的步骤：

1. 在飞书桌面端点自己的**头像** → **登录更多账号**（左下角有其他账号时，是 `+ 登录更多账号`）
2. 点 **创建新账号**（不要点「加入企业」）
3. 输入手机号，收验证码，验证
4. 角色选 **企业/团队/组织负责人**，点「开始使用」—— 到这一步企业就已经建好了
5. 弹窗里填姓名和企业名称，比如 `CRM-Dev`
6. 邀请成员那一步直接点「稍后邀请」跳过，这个租户只有你一个人

建完之后你就是这个企业的创建人兼第一位超级管理员，头像菜单里会出现「管理后台」。

几个容易踩的点：

- **不要用公司邮箱**去认领或加入任何组织，否则可能被并进公司租户，权限又回到 IT 手上
- **不需要企业认证**（营业执照那一套）。未认证的基础免费版就能开本项目要的全部权限
- 同一个手机号，创建的企业加上加入的企业**总数不超过 30 个**
- 飞书（feishu.cn）创建企业**只支持 +86 手机号**。如果你手上只有港号，走 Lark 国际版 [larksuite.com](https://www.larksuite.com/)，流程一样，开发者后台是 open.larksuite.com，权限标识和事件名完全一致

### 应用和多维表格必须在同一个租户里

这条不写清楚很容易白干半天。官方定义：「企业自建应用……**只能在同一企业内发布和使用**。」

所以在 `CRM-Dev` 里建的应用，只能被加成 `CRM-Dev` 这个租户里的多维表格的协作者。你**不能**用它去读公司租户里那张真实的佣金表。阶段 A 的正确做法是在新建的租户里自己建一个空 Base、把结构建起来（第 7、9 步）、再造一套测试数据（第 10 步）；等阶段 B 公司审批通过后，在公司租户里重建一个应用，只换 `.env` 里的凭证，代码一行不改。

## 第 2 步：创建自建应用

1. 打开 https://open.feishu.cn/app ，用刚才建的那个账号登录
2. 「创建企业自建应用」，名称填 `CRM 渠道佣金助手`
3. 建好后进入应用，左侧「凭证与基础信息」，记下 **App ID** 和 **App Secret**

创建时会弹一个确认框，写着「该应用仅在 XXX 内可用……」。**看清楚 XXX 是不是你刚建的团队名**。如果它显示的是 `飞书个人版`，说明浏览器还挂在旧账号上 —— 开发者后台跟着当前登录身份走，切了客户端不等于切了网页。退出重新登录，或者用无痕窗口重来。

把这两个填进项目根目录的 `.env`：

```bash
cp .env.example .env
```

```
LARK_APP_ID=cli_xxxxxxxxxxxxxxxx
LARK_APP_SECRET=你的secret
```

> `.env` 已在 `.gitignore` 里。永远不要提交它，也不要贴进聊天记录。

## 第 3 步：开启机器人能力

左侧「添加应用能力」→「机器人」→ 启用。

销售全部通过这个机器人交互，不需要网页应用或小程序。

## 第 4 步：开权限

左侧「权限管理」，搜索并开通下面这些。**一次开齐**，免得后面反复发版本。

| 权限标识 | 用途 |
| --- | --- |
| `bitable:app` | 读写多维表格。渠道、客户、佣金、审计全靠它 |
| `im:message` | 接收销售发给机器人的消息 |
| `im:message:send_as_bot` | 以机器人身份发消息和卡片 |
| `contact:user.base:readonly` | 读销售的姓名，卡片上显示「张三，你登记的渠道是 R010」 |

## 第 5 步：订阅事件与回调

左侧「事件与回调」。注意这里是**两个独立的页面**，要各配一次，很多人只配了前一个然后卡在卡片没反应上：

| 页面 | 配什么 | 用途 |
| --- | --- | --- |
| 事件与回调 > **事件配置** | `im.message.receive_v1` | 销售给机器人发消息时触发，用来弹出登记卡片 |
| 事件与回调 > **回调配置** | `card.action.trigger` | 销售点卡片上的提交按钮时触发，**这是数据录入的主通道** |

**两个页面的订阅方式都选「使用长连接接收事件」。**

这一点很关键，不是图省事：公司内网服务器没有公网入口，飞书的 webhook 根本打不进来。长连接只需要服务器能**出网**，本地开发和内网生产用的是同一套机制，代码不用改。

长连接的官方限制有三条值得记住：只支持企业自建应用（商店应用不行）；收到消息后必须 3 秒内处理完且不抛异常，否则触发超时重推；同一应用起多个客户端是集群模式不是广播，只有随机一个会收到消息 —— 所以生产环境别为了「高可用」起两个进程。

另外，旧版的「消息卡片回传交互（旧）」回调不支持长连接。本项目用的是新版 `card.action.trigger`，不受这条限制。

> 保存「使用长连接接收事件」时，本地必须有一个已连上的程序在跑，否则保存会失败。先执行下一步的连通性测试，让程序连上，再回来点保存。

## 第 6 步：验证连通性

```bash
uv sync
uv run python scripts/ws_smoke.py
```

看到 `长连接已建立` 就说明 App ID / Secret 正确、网络通了。保持它运行，回到第 5 步保存订阅方式。

然后在飞书里给机器人发一条消息，`ws_smoke.py` 会回你一张带表单的卡片。**点一下提交按钮** —— 如果收到 toast 提示而不是 `200340 出错了，请稍后重试`，说明 CARD 帧补丁生效了，这是最关键的一道验证。

**顺手把日志里那行 open_id 抄下来。** 你发消息时 `ws_smoke.py` 会把发件人的 `open_id`（`ou_` 开头的一长串）打出来，第 10 步造种子数据要用它，机器人的归属鉴权也全靠它。现在不抄，等下还得再跑一遍。

## 第 7 步：拿到 Base 的 token

在 `CRM-Dev` 这个租户里**新建一个空的多维表格**（云文档 → 新建 → 多维表格）。不要去找公司那张真表 —— 跨租户读不到，理由见第 1 步末尾。

打开它，看地址栏：

```
https://xxx.feishu.cn/base/bascnABC123XYZ?table=tblDEF456&view=vewGHI789
                            ^^^^^^^^^^^^^^        ^^^^^^^^^
                            APP_TOKEN             TABLE_ID
```

`.env` 里填 `LARK_BASE_APP_TOKEN=bascnABC123XYZ`。

**还要把应用加成这个 Base 的协作者**，否则应用读不到：在多维表格右上角「...」→「添加文档应用」→ 搜索你的应用名 → 添加，权限给「可编辑」。

> 这一步最容易漏。漏了的话 API 会返回权限错误，而错误信息不会直说是没加协作者。

## 第 8 步：探查 Base 结构

```bash
uv run python scripts/inspect_base.py
```

它会列出这个 Base 里所有的表和字段类型，并写一份快照到 `schema_snapshot.json`（已 gitignore，因为可能含真实客户数据）。

刚建的空 Base 这一步会很短，那是正常的 —— 它真正的价值在阶段 C：接上公司那个已经有一堆表的 Base 时，先看清现状再动手。

## 第 9 步：建表

```bash
uv run python scripts/sync_base.py          # 预演，打印将要建什么
uv run python scripts/sync_base.py --apply  # 执行
```

只增不改不删：缺的表和字段会补，已存在但类型不符的只报告给你决定，多出来的一概不碰。建出来的五张表和每个设计选择的理由，见 [SCHEMA.md](SCHEMA.md)。

注意它**不建**交易明细表。那是同事维护的表，我们只读；真跑到公司 Base 上建一张同名表会盖住同事的表。开发租户里那张模拟的交易明细表由下一步负责。

## 第 10 步：造种子数据

```bash
# 预演，不写任何东西
uv run python scripts/seed_dev_data.py --open-id ou_你的openid

# 确认无误后真的写
uv run python scripts/seed_dev_data.py --open-id ou_你的openid --yes-this-is-a-dev-base
```

`--open-id` 用第 6 步抄下来的那串。渠道和客户会挂在这个人名下，机器人按 open_id 过滤归属，不填的话你用机器人查「我的渠道」会是空的。实在拿不到就加 `--no-open-id` 先跑起来，之后再 `--reset` 重来一次。

### 为什么必须造，为什么必须走 API

第 1 步末尾那条限制在这里第二次咬人：自建应用只能在同一企业内使用，`CRM-Dev` 里的应用**读不到**公司租户那张真实的交易明细表。阶段 A 想验证对账，就只能在开发租户里自己造一份。

那从公司表导出 CSV 再导进来行不行？不行，而且这是这个项目里最贵的坑：Excel 只保留 15 位有效数字，18-19 位的客户UID 一过 Excel 就被抹掉低位 —— `577809207768677761` 变成 `577809207768678000`。抹完之后它看起来仍然是个合法的长数字，join 时静默匹配到别的客户。测试数据从第一天起就是坏的，而且坏得看不出来。

走 API 直接写就没有这个问题：Python 的 `int` 和 `str` 都是任意精度，全程不经过任何浮点数环节。

### 它造了什么

| 表 | 内容 |
| --- | --- |
| Referral Information | 4 个渠道，分佣比例 20 / 12.5 / 15 / 8，其中一个留在「待审核」 |
| Referred Client | 7 个客户，UID 是 18-19 位的真实形态 |
| Transaction Details | **新建的模拟表**，字段名和类型对齐真表；30 笔交易，跨 2026-01 到 03 |
| Audit Log | 11 条，对应上面每一次登记 |
| Sales Directory | 你自己（管理员）+ 2 个假账号，其中一个「停用」 |
| Commission Summary | **刻意留空**，由 `reconcile --write` 填 |

数据是照着「能暴露问题」设计的，不是随便编的几行：

- 有两对**只差最后一位**、且分属不同渠道的客户UID（`577809207768677761` / `...762`）。谁哪天在链路上做了一次 `int()`，这两个值会塌成同一个，佣金立刻算到隔壁渠道头上 —— 而且是对账输出里看得见的错。如果 UID 都长得八竿子打不着，精度丢了只是匹配不上，很容易被当成「数据还没导全」
- 有 3 个客户只出现在交易明细里、没登记归属渠道，用来验证 `reconcile` 的 unmapped 告警真的会响
- 有 6 笔亏损单（负 Pnl），其中恒星资本 2026-02 整月合计为负 `-2935.10`，会算出一个**负的应付佣金** `-440.27`。这不是 bug，是一个还没定的业务规则，见下

### 两道安全闸门

这个脚本会写数据，所以默认只预演，且加了两道锁：

1. 必须显式传 `--yes-this-is-a-dev-base` 才真写
2. 执行前扫一遍目标 Base，发现任何不是它造的记录就拒绝执行

两道防的不是同一件事。flag 防的是「不知道这脚本会写数据」，但防不住最现实的那种失误：从文档里复制了完整正确的命令，而 `.env` 里的 `LARK_BASE_APP_TOKEN` 指着生产 Base —— flag 照样传了，人的意图也没错，错的是目标。只有真去读一眼目标 Base 里有什么才拦得住。反过来只有扫描也不够，因为一个刚建好的生产 Base 也是空的。

**没有跳过第二道检查的开关。** 有开关就一定会有人在生产上用它。

### 重复执行

重复跑是安全的：按自然键跳过已存在的行（渠道按名称、客户按 UID、交易按「日期+UID+Pnl」、销售按 OpenID），只补缺的，不会堆出重复数据。

要换一套种子数据重来，用 `--reset`：

```bash
uv run python scripts/seed_dev_data.py --open-id ou_xxx --yes-this-is-a-dev-base --reset
```

它只删标记字段以 `SEED-` 开头的记录 —— 所有种子行的名称都带这个前缀，所以就算指错了 Base 也删不掉任何真实数据。删之前还会要你**手敲一遍 app_token**：整行命令可以复制粘贴，多加一个 flag 只是让那行更长，而 app_token 得从 `.env` 里翻出来对着敲，敲的过程本身就是一次核对。

## 第 11 步：跑一次对账

```bash
uv run python -m crm_basebot.jobs.reconcile --period 2026-02
```

默认只算不写。预期看到 3 个未登记归属的客户告警，以及恒星资本那个负数。确认无误再加 `--write`。

### 关于负 Pnl，需要业务定一件事

现在的算法是直接把当月 Pnl 合计乘以分佣比例（`domain/commission.py` 的 `CommissionRow.payable`），所以整月亏损的渠道会得到一个负的应付佣金。代码没有报错，也没有任何注释说这是有意的。可能的规则至少有三种：

1. 负数就是负数，渠道倒欠我们钱（当前行为）
2. 单月按 `max(0, ...)` 计，亏损月不倒扣
3. 亏损结转到下个月，从后续佣金里冲抵

三种算出来的钱差很多。种子数据保证这个情形每次对账都会出现，逼它被看见，但**不替业务拍板**。

另外顺带暴露的一件事：佣金计算不看渠道状态，「待审核」和「停用」的渠道照样会被算进汇总（种子数据里的灰岩科技就是待审核）。这同样是一个待确认的业务规则。

## 排查

**`99991663` 或提示 token 无效** — App ID / Secret 填错了，或者 `.env` 没被读到（确认在项目根目录）。

**读 Base 报权限错误** — 第 7 步的「添加文档应用」没做。

**点卡片按钮报 `200340`** — CARD 帧补丁没生效。跑 `uv run pytest tests/test_ws_patch.py -v` 看补丁状态。如果测试提示 SDK 已官方修复，说明补丁被自动跳过了但 SDK 的修复方式和我们预期不同，需要重新看一下 `ws_patch.py`。

**保存「使用长连接接收事件」失败** — 本地程序没在跑，或者跑起来了但没连上。先让 `ws_smoke.py` 打印出「长连接已建立」再去保存。

**改了权限后不生效** — 自建应用改权限需要「创建版本并发布」，在自己的组织里你就是审核人，点一下通过即可。发布后可能要几十秒生效。

**创建应用时提示只在「飞书个人版」内可用** — 你当前登录的是个人版租户，不是团队租户。回到第 1 步。

**`seed_dev_data.py` 说「这个 Base 里有不是本脚本造的数据」** — 先确认 `.env` 里的 `LARK_BASE_APP_TOKEN` 指的是你自己那个 Base，不是公司的。确认没指错的话，那就是你之前用机器人手动登记过东西了：要么自己去 Base 里删掉那几行，要么新建一个空 Base 重来。这道检查没有跳过开关，是故意的。

**种子数据造好了，但机器人查「我的渠道」是空的** — `--open-id` 没传或者传错了。归属是按 open_id 精确比对的。用 `--reset` 重跑一次，这次带上第 6 步日志里那串 `ou_` 开头的值。

**`99991403` / HTTP 429，`This month's API call quota has been exceeded`** — 本月 API 调用量用完了，见下面的附录。

## 附录：免费版的 API 调用额度

基础免费版按**租户**计额度，一个租户下所有自建应用的调用量合并计算，每个自然月 1 号清零重置。基线是 1 万次/月，飞书会不定期做限时提额（官方《[自建应用 API 调用量上限调整说明](https://open.feishu.cn/document/platform-notices/platform-updates-/custom-app-api-call-limit)》上出现过 5 万和 100 万的临时值）。实际额度以管理后台 **费用中心 > 权益数据** 页面显示的为准，别照抄任何文章里的数字。

超限后返回 HTTP `429` + 错误码 `99991403`，调用直接失败，要等下个月 1 号恢复。用量到 90% 和 100% 时开放平台会给管理员和开发者推卡片提醒。

有几类接口**不计入**调用量，即使额度耗尽也能继续调：认证及授权、事件订阅、通讯录、飞书人事、招聘、绩效、智能门禁、飞书应用引擎、AI 能力。

对本项目来说这意味着：

- `contact:user.base:readonly` 走通讯录，**不计费**
- `im.message.receive_v1` 和 `card.action.trigger` 走事件订阅，**不计费**
- 多维表格读写（`bitable:app`）和发消息发卡片（`im`）**计费**，这是主要消耗

一次登记大致是几次 Base 读 + 一次写 + 一次发卡片，量级在个位数。开发测试阶段撞不到上限。真正要留意的是对账任务：`reconcile` 会全量拉表，跑之前先想一下记录条数乘以分页次数。
