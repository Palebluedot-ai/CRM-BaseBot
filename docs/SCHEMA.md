# 表结构

字段名的唯一权威出处是 [`src/crm_basebot/domain/schema.py`](../src/crm_basebot/domain/schema.py)。这份文档解释**为什么**这么设计，代码里放的是**是什么**。改字段名请改代码，这里跟着更新。

## 关系

```
Transaction Details ──客户UID──► Referred Client ──关联──► Referral Information
   (同事维护，只读)                  (bot 写入)              (bot 写入，含分佣比例)
                                                                    │
                                          Pnl(USD) × 分佣比例，按月聚合
                                                                    ▼
                                                        Commission Summary
```

## 表 1：Referral Information（渠道登记）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 渠道编号 | 自动编号 | `R` + 3 位。递增由飞书系统保证 |
| 渠道名称 | 文本 | |
| 邮箱 | 文本 | |
| 地址 | 文本 | 合同和付款用 |
| 收款信息 | 文本 | 银行账户或钱包地址 |
| 分佣比例 | 数字 | 百分数，20 表示 20% |
| 归属销售 | 人员 | 由 open_id 自动填，销售不能自选 |
| 登记人OpenID | 文本 | 冗余一份用于代码里的归属校验 |
| 状态 | 单选 | 生效 / 停用 |

**为什么编号用自动编号字段而不是自己算**：多个销售可能同时提交，自己读最大值再加一存在竞态。Bitable 的自动编号是服务端生成的，天然没有这个问题。代价是它不能通过 API 写入，所以 `create_record` 写完要回读一次才能把编号回显给销售。

**为什么归属存两份**（人员字段 + OpenID 文本）：人员字段是给人在 Base 里看的，OpenID 文本是给代码做精确比对的。人员字段的返回结构在不同接口下不一致，拿它做鉴权判断容易出错。

**为什么没有「待审核」**：登记即生效，不设管理员过目这一步（2026-09-04 定的）。佣金计算也不看状态；停掉的渠道按业务约定根本不在数据里。

## 表 2：Referred Client（渠道介绍的客户）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 客户UID | **文本** | 与交易明细 join 的键 |
| 客户名称 | 文本 | |
| 所属渠道 | 单向关联 | 指向表 1 |
| 归属销售 | 人员 | |
| 登记人OpenID | 文本 | |

**客户UID 必须是文本，不能是数字。** 实际值是 18–19 位（`577809207768677761`、`2141293991366272768`），超过 float64 能精确表示的整数上限 2^53（约 9.0e15，16 位）。存成数字字段的话，精度在 Bitable 服务端就已经丢了，客户端补救不了 —— 而丢精度后的值看起来仍然是个合法长数字，join 时会静默匹配到别的客户。

`scripts/inspect_base.py` 会专门检查这一点并报警。

## 表 3：Transaction Details（交易明细）

同事每天手工导入，**我们只读，从不写**。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| 订单时间 | 日期 | 归月 |
| 名称 | 文本 | 我方主体，如 HashKey SG |
| 客户名称 | 文本 | 人看的 |
| 客户UID | 查找引用 | **join 键** |
| HTS 获得数量 | 数字 | 不参与佣金 |
| 价格 | 数字 | 不参与佣金 |
| 手续费 | 数字 | 不参与佣金 |
| 手续费币种 | 文本 | |
| Pnl(USD) | 数字 | **佣金基数** |

算佣金真正依赖的只有三个：订单时间、客户UID、Pnl(USD)。`jobs/reconcile.py` 在计算前会调 `assert_fields_present` 校验这三个还在、类型没变，对不上就中止 —— 这张表不在我们控制下，静默算错比报错危险得多。

阶段 A 的开发租户里读不到这张表（自建应用跨不了租户），所以 `scripts/seed_dev_data.py` 会在那边建一张同名同字段的模拟表顶上，对账代码一行不用改。唯一的偏差是客户UID 建成「文本」而不是真表的「查找引用」—— 两种 `to_uid` 都能安全取值，`TXN_REQUIRED_FIELDS` 对它的期望类型也是 None。`sync_base.py` 永远不建这张表，免得在公司 Base 上盖掉同事的。

## 表 4：Commission Summary（佣金汇总）

后端按月写入。

| 字段 | 类型 |
| --- | --- |
| 结算月份 | 文本（YYYY-MM） |
| 渠道编号 | 文本 |
| 渠道名称 | 文本 |
| 客户数 | 数字 |
| 交易笔数 | 数字 |
| Pnl合计 | 数字 |
| 分佣比例 | 数字 |
| 应付佣金 | 数字 |
| 计算时间 | 日期 |

**结算月份怎么归**：订单时间先换算到 `.env` 里 `BUSINESS_TIMEZONE` 指定的时区（默认 `Asia/Singapore`，2026-09-04 定的）再取年月。Bitable 日期字段存的是 UTC 时间戳，直接按 UTC 取月份的话，本地每个月 1 号 0 点到 8 点的交易会全部算进上个月。

`应付佣金 = max(0, Pnl合计 × 分佣比例)`。整月亏损的渠道佣金按 0 保底，不倒扣也不结转到下个月 —— 这是业务规则（2026-08-30 定的），不是代码漏了处理负数。注意 `Pnl合计` **仍然如实记负值**：报表上要看得见这个渠道当月是亏的，把 Pnl 也截成 0 会让对账说不清账。完整说明见 `domain/commission.py` 的 `CommissionRow.payable`。

**为什么不在 Base 里用公式算**：Bitable 的 `FILTER` 上限 2 万条，单表也有行数上限，而交易明细是全量表且只增不减。后端聚合后只写少量汇总行，既避开上限，也让计算逻辑可被单元测试覆盖（见 `tests/test_commission.py`）。

金额在后端用 `Decimal` 累加而不是 float —— 上千行浮点累加的误差会让对账对不上分。

## 表 5：Audit Log（审计）

只增不改。机器人不提供任何修改或删除审计记录的入口。

| 字段 | 类型 |
| --- | --- |
| 时间 | 日期 |
| 操作人OpenID | 文本 |
| 操作人 | 文本 |
| 动作 | 文本 |
| 目标表 | 文本 |
| 目标记录 | 文本 |
| 详情 | 文本（JSON） |

审计**先于**业务写入。如果业务成功而审计失败，就出现了没有记录的变更；反过来留一条「尝试过」的记录是可接受的。

## 表 6：Sales Directory（销售名册）

open_id 到身份的映射，是鉴权的基础。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| OpenID | 文本 | 飞书平台签发的用户标识 |
| 姓名 | 文本 | |
| 角色 | 单选 | 销售 / 管理员 |
| 状态 | 单选 | 在职 / 停用 |

**名册里没有的人一律拒绝**，不做「默认放行」。新人要先被登记进来才能用机器人，这样「谁能用」始终是一个可查的清单。管理员角色不受归属限制，能看全部数据。

拿 open_id 最简单的办法：让本人给机器人发条消息，`scripts/ws_smoke.py` 会把 open_id 打到日志里。

## 建表

```bash
uv run python scripts/inspect_base.py      # 先看现状
uv run python scripts/sync_base.py         # 预演要建什么
uv run python scripts/sync_base.py --apply # 执行
```

`sync_base.py` 只增不改不删：缺的表和字段会补，已存在但类型不符的只报告给你决定，多出来的一概不碰。

结构建好之后，开发租户还需要一套测试数据才能验证对账，见 [LARK_APP_SETUP.md 第 10 步](LARK_APP_SETUP.md#第-10-步造种子数据)。
