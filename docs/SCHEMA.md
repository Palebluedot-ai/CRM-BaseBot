# 表结构

字段名的唯一权威出处是 [`src/crm_basebot/domain/schema.py`](../src/crm_basebot/domain/schema.py)。这份文档解释**为什么**这么设计，代码里放的是**是什么**。改字段名请改代码，这里跟着更新。

## 关系

```
Daily Revenue Board ──用户ID──► Referred Client ──关联──► Referral Information
   (脚本每天从 xlsx 导入)          (bot 写入)              (bot 写入，含分佣比例)
                                                                    │
                                     总收入(opt+现货+合约) × 分佣比例，按月聚合
                                                                    ▼
                                                        Commission Summary
```

**基数从 Pnl 切到毛收入是 2026-09-09 的业务决定**。原方案按 Pnl(USD) 算，
现在按看板里已经聚合好的「总收入(opt+现货+合约)」算 —— 使用方明确要求按毛收入分佣。
2026-09-17 起看板表头以真实导出为准，这一列的名字多了「+合约」；合约两列目前全是 0，算出来的钱不变。
`max(0, ...)` 保底条款保留（见表 4）。

## 表 1：Referral Information（渠道登记）

列对齐 2026-09-17 给的模板「Referral Registration」，现成的 101 个渠道由 `scripts/import_registrations.py` 导入，重复跑只更新不重复。

| 字段 | 类型 | 模板里的列 | 说明 |
| --- | --- | --- | --- |
| 渠道编号 | **文本** | Referral Code | `R` + 3 位。现成的 R001-R101 直接导入；机器人新登记时读最大号 +1 |
| 渠道名称 | 文本 | Name | |
| 邮箱 | 文本 | Email | 模板里这一列的表头被覆盖成了一个邮箱地址，导入按「含 email」认 |
| 地址 | 文本 | 无 | 模板里没有，机器人登记表单还在收 |
| 收款信息 | 文本 | 无 | 同上 |
| 开始日期 | 日期 | Start Date | 存业务时区那天的零点 |
| 分佣比例 | 数字 | Commission Rate | 百分数，20 表示 20%。模板里是小数 0.2，导入时乘 100 |
| 结算频率 | 单选 | Payout Frequency | Monthly / Quarterly |
| 提交日期 | 日期 | Submitted On | |
| 负责销售 | 文本 | Sales In Charge | 姓名。OpenID 补上之前先靠它对人 |
| 归属销售 | 人员 | 无 | 由 open_id 自动填，销售不能自选；导入的行先空着 |
| 登记人OpenID | 文本 | 无 | 冗余一份用于代码里的归属校验；导入的行先空着 |
| 状态 | 单选 | 无 | 生效 / 停用。导入时名字带 TERMINATED 的记为停用 |

**为什么编号是文本而不是自动编号**：现成的渠道已经有编号 R001-R101，自动编号列由飞书服务端生成、写不进去。所以编号列是文本，机器人新登记时读当前最大号 +1，在进程级写锁的临界区里串行执行，不会撞号（2026-09-17 定的）。`.env` 里 `REFERRAL_AUTO_NUMBER` 保持 false。

**为什么归属存两份**（人员字段 + OpenID 文本）：人员字段是给人在 Base 里看的，OpenID 文本是给代码做精确比对的。人员字段的返回结构在不同接口下不一致，拿它做鉴权判断容易出错。

**为什么没有「待审核」**：登记即生效，不设管理员过目这一步（2026-09-04 定的）。佣金计算也不看状态；停掉的渠道按业务约定根本不在数据里。

## 表 2：Referred Client（渠道介绍的客户）

列对齐模板「Referred Clients」。模板里的 Name of Referral 不单独存，关联字段会显示渠道表的主字段「R001 名称」。

| 字段 | 类型 | 模板里的列 | 说明 |
| --- | --- | --- | --- |
| 客户UID | **文本** | UID | 与日读看板的「用户ID」join 的键。模板里空着时按客户名从「用户UID」表补 |
| 客户名称 | 文本 | Client Name | |
| 所属渠道 | 单向关联 | Referral Code | 指向表 1 |
| 负责销售 | 文本 | Sales In Charge | 姓名 |
| 归属销售 | 人员 | 无 | 导入的行先空着 |
| 登记人OpenID | 文本 | 无 | 导入的行先空着 |

**客户UID 必须是文本，不能是数字。** 实际值是 18–19 位（`577809207768677761`、`2141293991366272768`），超过 float64 能精确表示的整数上限 2^53（约 9.0e15，16 位）。存成数字字段的话，精度在 Bitable 服务端就已经丢了，客户端补救不了 —— 而丢精度后的值看起来仍然是个合法长数字，join 时会静默匹配到别的客户。

同样的道理，UID 经不起 Excel：存成数字读回来是浮点数，`import_registrations.py` 直接报错停下；贴成文本但尾巴一串 0 或科学计数法的，导入时不采用并提示。

`scripts/inspect_base.py` 会专门检查这一点并报警。

## 表 3：Daily Revenue Board（日读看板）

由 `scripts/import_daily_board.py` 从内部系统导出的交易明细 xlsx 导入。**列名和列顺序逐字照抄那份导出的表头**，以 2026-09-17 的「OTC组销售明细」为准，Base 里不做任何改名：拿着 Excel 就能在 Base 里找到同一列。导出里少任何一列，导入直接拒绝并点名；多出来的列忽略。

**只放新加坡站的记录**（2026-09-17 定的）。导出里有香港站、新加坡站、中东站，导入时只保留「站点」是新加坡站的行，其他站点不进 Base。筛的是站点，不是销售分组：新加坡站的记录里也有 HK组、支付组的销售。那份导出 12,276 行里新加坡站是 1,628 行。

粒度是「一个用户在一个交易日」，但同一用户同一天可能有多行，那份导出里有 402 组。

| 列 | 类型 | 用途 |
| --- | --- | --- |
| 站点 | 文本 | 只有新加坡站，其他站点导入时丢掉 |
| 用户ID | **文本** | **join 键**，对应客户表的「客户UID」 |
| 交易日期 | 日期 | 归月。存业务时区那天的零点，见下 |
| 销售 | 文本 | 展示用；佣金归属仍走渠道 |
| 客户名称 | 文本 | 人看的，可能为空 |
| KYC日期 | 日期 | 展示用，可能为空 |
| 销售分组 | 文本 | HK组 / SG组 / 支付组 |
| 用户类型 | 文本 | 平台介绍客户 / 自主开发客户，目前不参与佣金计算 |
| 现货手续费_剔除做市商 | 数字 | 总收入的组成部分 |
| 现货交易额_剔除做市商 | 数字 | 总交易额的组成部分 |
| 合约手续费_剔除做市商 | 数字 | 总收入的组成部分，目前全是 0 |
| 合约交易额_剔除做市商 | 数字 | 总交易额的组成部分，目前全是 0 |
| opt手续费 | 数字 | opt_pnl 为空时等于 opt收入 |
| opt_pnl | 数字 | 可能为空 |
| opt收入 | 数字 | 总收入的组成部分 |
| opt交易额 | 数字 | 总交易额的组成部分 |
| 总收入(opt+现货+合约) | 数字 | **佣金基数** |
| 总交易额(opt+现货+合约) | 数字 | 展示用 |

那份导出里这两条关系一行不差：`总收入 = opt收入 + 现货手续费_剔除做市商 + 合约手续费_剔除做市商`，`总交易额 = opt交易额 + 现货交易额_剔除做市商 + 合约交易额_剔除做市商`。种子数据按同样的关系造。

算佣金真正依赖的只有三个：交易日期、用户ID、总收入(opt+现货+合约)。`jobs/reconcile.py` 在计算前会调 `assert_fields_present` 校验这三个还在、类型没变，对不上就中止。

**为什么必须走 xlsx 不走 CSV**：用户ID 大多是 18-19 位数字。CSV 在源头几乎总是过 Excel，ID 的低位在存成 CSV 之前就被抹成 0 了，下游修不了。xlsx 保留原生类型，只要用户ID 那一列是文本就拿得到原值；存成数字的长 ID 读回来一定是浮点数，`import_daily_board.py` 直接拒绝。那份导出里也有五到七位的短用户ID，照常导入。

**幂等策略**：按交易日期区间「先删后写」。同一天的行可能被多次修正，又没有稳定的行主键，按日期批量替换是最简单也最安全的语义。替换的是导出覆盖到的所有日期，包括那天只有其他站点记录的日子：导出说这天新加坡站没有记录，Base 里这天的旧记录就该清掉。筛完一行新加坡站都不剩时拒绝导入，免得把这些日期删光。

**批量写**：删除和写入都按每批 500 条发。一行一个请求的话，1.2 万行的导出一次就是 1.2 万次调用，而免费版每月的基线额度是 1 万次，见 [LARK_APP_SETUP.md 附录](LARK_APP_SETUP.md#附录免费版的-api-调用额度)。

**日期按业务时区**：交易日期和 KYC日期是新加坡的日历日，导入时写成 `BUSINESS_TIMEZONE` 那一天的零点，先删后写也按这个时区取日期（2026-09-14 定的）。按 UTC 算的话，界面里手工填的日期是新加坡零点，会被算成前一天，重导时删不掉它。换算收在 `domain/dates.py`，种子数据用同一约定。

## 表 4：Commission Summary（佣金汇总）

后端按月写入。同一月份重跑时 `--write` 会拒绝在旁边再写一套；加 `--replace` 先删该月旧行再写，`--all-periods --replace` 清空整张表（2026-09-05 定的）。

| 字段 | 类型 |
| --- | --- |
| 结算月份 | 文本（YYYY-MM） |
| 渠道编号 | 文本 |
| 渠道名称 | 文本 |
| 客户数 | 数字 |
| 记录笔数 | 数字 |
| 总收入合计 | 数字 |
| 分佣比例 | 数字 |
| 应付佣金 | 数字 |
| 计算时间 | 日期 |

**结算月份怎么归**：交易日期先换算到 `.env` 里 `BUSINESS_TIMEZONE` 指定的时区（默认 `Asia/Singapore`，2026-09-04 定的）再取年月。Bitable 日期字段存的是 UTC 时间戳，直接按 UTC 取月份的话，本地每个月 1 号 0 点到 8 点的交易会全部算进上个月。

`应付佣金 = max(0, 总收入合计 × 分佣比例)`。整月合计为负的渠道佣金按 0 保底，不倒扣也不结转到下个月 —— 这是业务规则（2026-08-30 定的），不是代码漏了处理负数。注意 `总收入合计` **仍然如实记负值**：报表上要看得见这个渠道当月是负的（退款/冲销/校准场景），把它也截成 0 会让对账说不清账。完整说明见 `domain/commission.py` 的 `CommissionRow.payable`。

原基数是 `Pnl(USD)`；2026-09-09 切成毛收入之后，`max(0, ...)` 保底大多数月份是空转，但规则条款不变 —— 退款/冲销那种边界情况仍然要兜住。

**为什么不在 Base 里用公式算**：Bitable 的 `FILTER` 上限 2 万条，单表也有行数上限，而日读看板是每天追加的表且只会越来越长。后端聚合后只写少量汇总行，既避开上限，也让计算逻辑可被单元测试覆盖（见 `tests/test_commission.py`）。

金额在后端用 `Decimal` 累加而不是 float —— 上千行浮点累加的误差会让对账对不上分。

## 表 5：Audit Log（审计）

只增不改。机器人不提供任何修改或删除审计记录的入口。

| 字段 | 类型 |
| --- | --- |
| 时间 | 日期 |
| 操作人OpenID | 文本 |
| 操作人 | 文本 |
| 动作 | 文本 |
| 目标表 | 文本 |
| 目标记录 | 文本 |
| 详情 | 文本（JSON） |

审计**先于**业务写入。如果业务成功而审计失败，就出现了没有记录的变更；反过来留一条「尝试过」的记录是可接受的。

## 表 6：Sales Directory（销售名册）

open_id 到身份的映射，是鉴权的基础。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| OpenID | 文本 | 飞书平台签发的用户标识 |
| 姓名 | 文本 | |
| 角色 | 单选 | 销售 / 管理员 |
| 状态 | 单选 | 在职 / 停用 |

**名册里没有的人一律拒绝**，不做「默认放行」。新人要先被登记进来才能用机器人，这样「谁能用」始终是一个可查的清单。管理员角色不受归属限制，能看全部数据。名册改了最多一分钟后生效（机器人缓存名册 60 秒），不用重启。

拿 open_id 最简单的办法：让本人给机器人发条消息，`scripts/ws_smoke.py` 会把 open_id 打到日志里。

## 建表

```bash
uv run python scripts/inspect_base.py      # 先看现状
uv run python scripts/sync_base.py         # 预演要建什么
uv run python scripts/sync_base.py --apply # 执行
```

`sync_base.py` 只增不改不删：缺的表和字段会补，已存在但类型不符的只报告给你决定，多出来的一概不碰。

结构建好之后，开发租户还需要一套测试数据才能验证对账，见 [LARK_APP_SETUP.md 第 10 步](LARK_APP_SETUP.md#第-10-步造种子数据)。
