# 阶段 B：IT / 管理员审批申请材料

这份文档是给公司 IT 和飞书管理员看的。目标是**一次过审**，所以把他们会问的问题提前答完。

申请前请先在自建的免费组织里把功能跑通（见 [LARK_APP_SETUP.md](LARK_APP_SETUP.md)），带着能演示的成品去谈，通过率完全不一样。

---

## 一、申请事项

在公司飞书租户内创建一个**企业自建应用**，名称建议 `CRM 渠道佣金助手`。

自建应用只能在本企业内发布使用，不上应用商店，不对外分发。

## 二、要解决的问题

渠道佣金的数据都在一个 Lark 多维表格里。业务上需要每个销售自己登记名下的渠道和渠道介绍的客户，但直接给销售开表格权限会有两个问题：

1. **数据越界**：多维表格的协作者默认能看到整张表，一个销售会看到所有同事的渠道、客户和佣金比例
2. **管理负担**：目前只有一名管理员，每加一个人、每调一次权限都要手工操作，容易出错且无记录

现有的替代方案是「行列权限」（多维表格高级权限），但它是手工配置、无版本记录、无法测试，且每次人员变动都要重新点一遍。

## 三、方案

销售**不成为多维表格的协作者**，只跟机器人对话。机器人代表应用身份读写表格，谁能看什么、谁能写什么由后端代码判定。

判定依据是飞书回调中的 `operator.open_id`。这个字段由飞书平台签发，客户端无法伪造，等同于一次平台级身份认证。后端据此只放行属于该销售自己的记录。

相比手工配权限，这个做法的好处是：权限规则是代码，可测试、可评审、每次变更都有 git 记录，符合变更留痕的要求。

## 四、申请的权限（最小集）

| 权限标识 | 用途 | 为什么必需 |
| --- | --- | --- |
| `bitable:app` | 读写指定的多维表格 | 登记数据要写入，佣金要读取汇总 |
| `im:message` | 接收销售发给机器人的消息 | 销售发消息唤起登记流程 |
| `im:message:send_as_bot` | 以机器人身份发送消息和卡片 | 返回登记表单和查询结果 |
| `contact:user.base:readonly` | 读取用户姓名等基础信息 | 卡片上显示操作人姓名，以及把 open_id 映射到销售身份 |

**没有申请**的权限，供对照：不读通讯录全量、不读聊天历史、不读日历邮件文件、不涉及人事考勤审批、不做任何对外发送。

`bitable:app` 的作用范围不是全租户 —— 应用只能访问被显式添加为协作者的那几个多维表格。管理员随时可以在文档协作者里移除应用，立即断开访问。

## 五、订阅的事件

| 事件 | 用途 |
| --- | --- |
| `im.message.receive_v1` | 销售给机器人发消息时触发 |
| `card.action.trigger` | 销售提交卡片表单时触发，主要的数据录入通道 |

## 六、网络与部署（IT 最关心的部分）

**订阅方式采用「长连接」，不使用 webhook。**

这意味着：

- **不需要开放任何入站端口**
- **不需要公网 IP 或域名**
- **不需要配置防火墙白名单或反向代理**
- **不需要内网穿透工具**

连接由内网服务器**主动向外**发起一条到飞书开放平台的 WebSocket，所有回调走这条既有连接下发。从网络视角看，它和一台服务器访问外部 HTTPS 服务没有区别。

服务器只需要能出网访问 `open.feishu.cn`。

如果贵司要求出网也走白名单，需要放行的域名就这一个。

## 七、数据流向

```
销售的飞书客户端
      │  (飞书内部链路)
      ▼
飞书开放平台
      │  (服务器主动建立的出站 WebSocket)
      ▼
公司内网服务器  ──────►  公司飞书租户内的多维表格
   (本应用)              (数据始终在飞书租户内)
```

**没有任何数据流向第三方。** 应用不调用任何外部 API，不上报遥测，不使用外部数据库或云服务。数据的存放位置仍然是公司飞书租户里的多维表格，和现在完全一样 —— 本应用只是改变了「谁能通过什么方式访问它」。

代码托管在公司账号可控的私有 Git 仓库，可供审阅。

## 八、风险控制

| 风险 | 控制措施 |
| --- | --- |
| 销售看到不属于自己的数据 | 销售不是表格协作者；后端按 `open_id` 过滤，有单元测试覆盖越权场景 |
| 销售篡改已生效的数据 | 机器人只开放新增，不开放直接修改。改数据走「提交申请 → 管理员确认」 |
| 交易明细被误改 | 应用对交易明细表**只读**，从不写入 |
| 操作无法追溯 | 每一次写入都先落一条审计记录（谁、何时、改了哪条、改前改后值），审计表只增不改 |
| 应用凭证泄露 | App Secret 存放在服务器本地环境变量文件，不入代码库；泄露时管理员可在开发者后台一键重置 |
| 需要紧急停用 | 管理员在多维表格协作者里移除应用即刻断开；或在管理后台停用应用 |

## 九、如果审批被卡住

按经验，最容易被追问的是 `bitable:app`，因为名字看起来像「所有多维表格」。回应要点：该权限受文档协作者约束，应用只能访问被明确添加进去的表格，管理员可随时移除，且移除是即时生效的。

第二容易被问的是「要不要开端口」。答案是不要 —— 见第六节，这通常是让 IT 放心的关键一条。

## 十、发布流程说明

自建应用的权限变更需要「创建版本 → 提交审核 → 管理员通过」。所以权限最好**一次申请齐全**，避免反复走流程。第四节的清单已经是跑通全部功能所需的完整集合。
