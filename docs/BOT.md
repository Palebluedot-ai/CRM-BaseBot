# Lark 机器人：现在能做什么，以及怎么才叫闭环

> **要给某位销售登记身份（open_id）？** 走 [docs/OPENID_ONBOARDING.md](OPENID_ONBOARDING.md)
> —— 那份规程每位销售、每换一个 Bot 都要走一遍，永久保留。本文只讲「现状与缺口」。

这份文档是对**已经存在的机器人代码**的梳理（不是设计提案）。目的是回答两个问题：

1. 渠道登记、引荐客户登记这些事，机器人现在能不能做？
2. 要让它真正闭环，还缺什么？

结论先说：**代码里的功能已经基本够用，缺的是「数据」和「上线」两件事**。这两件
2026-09-22 在 HashKey 租户里做完了：名册四个人的 OpenID 都收齐了，存量归属回填了
135 条，机器人也装成了 launchd 常驻。不需要重写。第四节逐条记着现状。

## 一、机器人现在能做什么

入口：给机器人发任意一条消息，回一张主菜单卡片。四个按钮对应四条路。

| 按钮 | 动作 | 写入 | 备注 |
|---|---|---|---|
| 登记新渠道 | `open_referral_form` | Referral Information 一行 | 名称、邮箱、开始日期、分佣比例、结算频率 |
| 登记新客户 | `open_client_form` | Referred Client 一行 | 先选自己名下的渠道，再填客户UID + 名称 |
| 我的渠道 | `list_referrals` | 只读 | 列出本人名下渠道（管理员看全部），一页 20 条、按钮紧贴；可点进详情 |
| 佣金查询 | `open_commission_query` | 只读 | 选月份，列出这个月和前两个月、本人名下每个渠道每个客户的应付**交易**佣金 |
| ECAS 返佣 | `open_ecas_query` | 只读 | 选月份，读 ECAS 申请表算本人名下各渠道应付返佣 |

ECAS 单独一个入口，**不并进「佣金查询」**：两笔钱、两套比例、两张汇总表
（见 [ECAS.md](ECAS.md)）。混在一个按钮后面，人分不清自己看的是哪一笔。
结果卡的标题色也不同（ECAS 是 turquoise，交易佣金是 blue），在会话里往上翻一眼分得开。

权限口径两边一致：只看**归属自己的渠道**，判据是渠道表的「登记人OpenID」，
不是 ECAS 表那一列「负责销售」—— 返佣付给渠道，谁经手那笔申请不决定谁该看到这笔钱。
没挂渠道的孤儿行对谁都不显示（结算那条路**会**算进去，两条路在这里刻意不一样）。

`.env` 里没有 `TABLE_ECAS` 时这个按钮回一句「未启用」，机器人照跑。

### 渠道详情卡：先钱，后资料（2026-09-24 两轮反馈）

点进一条渠道，第一眼要看的是它最近挣了多少、每个客户贡献了多少 —— 不是它的邮箱和
提交日期。所以卡片顺序是：

1. **近 3 个月**（含本月至今，从早到晚）—— 每个月一行合计，下面一张表：
   **客户 | 交易 | ECAS**，每个有记录的客户一行。两套账**分两列**，不合并（同一个渠道
   两边的比例可以不一样，合成一个数就看不出哪笔是哪笔）；同一个客户两边都有钱时排在
   同一行（先按 UID 对，ECAS 那边没填 UID 就按规整后的名字对）
2. **客户名单** —— 这条渠道下登记的客户，超过 15 个折叠
3. **渠道详情** —— 开始日期、分佣比例、结算频率、邮箱、提交日期

「是谁」「特别信息」两节按第二轮反馈删了；编号挪到标题下面的副标题。地址和收款信息
还在 Base 里，开发票去那里查。

近 3 个月是**现算**的，和「佣金查询」用同一段代码（`commission_query.accumulate` +
`ReferralBreakdown`：渠道级算应付、按收入占比分到客户，最大余数法保证各客户加起来一分
不差），所以两张卡上同一个渠道同一个月的数一定一样。本月还没结算，标「本月至今」。

**看板只读这条渠道的客户**：按客户UID 在服务端筛选（`iter_records_where_in`），不扫
整张上万行的看板。筛选接口出错时退回全表扫描 —— 慢，但数是对的，日志里留一行 WARNING。

这张卡要多读几张表，近 3 个月和客户名单各自包着 try：取不到就那一节不显示（近 3 个月会
说「这次没查到」），渠道资料照给。

### 列表：一页 20 条，按钮紧贴

一页八条要翻十三次，翻页本身比看渠道还累。

**但也不能一口气全列出来。** 改成一页 60 条之后飞书直接拒收整张卡：客户端弹
`200673`，服务端**一行日志都没有** —— 回调响应有上限，超了平台自己丢掉，我们这边
完全看不见。原作者那句「一页八条，卡片还放得下按钮」多半是同一堵墙撞出来的。

现在 20 条，是往回收的一档：比 8 条少翻三分之二，又离 60 这个已知会炸的值足够远。
**这个上限没有文档，只能试** —— 要再往上加，一次加十，每次都在真机上点一遍
「我的渠道」。改 `cards.REFERRAL_PAGE_SIZE`。

渠道按钮之间 `margin` 设成 `0px`：这一列是一整条名单，不是一堆各自独立的按钮。
六十个按钮各留 8px，光间距就多出快五百像素。只有一页时不显示「第 1/1 页」。

### 每点一下都是一条新消息，旧卡原样留着（2026-09-24 反馈）

卡片回调的返回值会**原地替换**被点的那张卡：点「我的渠道」，菜单就变成列表；点一条
渠道，列表就变成详情；查询表单点「查询」，就变成一张永远停在「正在查询」的卡。会话里
留不下任何记录 ——「看完渠道，紀錄會消失」。

所以现在回调**几乎不换卡**：立即回一个空响应（或者一句 toast），真正的内容在后台算好，
作为**新消息**推出去（`handlers._push`）。被点的卡原样留着，想再点还能点 —— 查询表单
可以换个月份再查，渠道列表可以接着点下一条。只有两处原地换：

| 原地换的 | 为什么 |
|---|---|
| 渠道列表的「上一页 / 下一页」（`referral_page`） | 翻的是同一张列表，不是做完了一件事 |
| 登记表单提交之后换成「已提交」回执 | 表单原样留着就能再点一次提交，登记出两条一样的渠道。回执把填过的内容一项项列出来，记录照样在；登记结果另发一条新消息 |

**填错了只弹一句红色 toast，表单原样留着**，改一个字就能再提交 —— 不再把整张表单换成
一张报错卡、让人从头填一遍。要读表才查得出的问题（UID 已经登记过、渠道不在你名下）
在后台查，结果卡说清楚。

新消息落在会话最底下，所以两种卡给的按钮不一样，因为「下一步」本来就不一样：

| 卡片 | 给什么 | 为什么 |
|---|---|---|
| **导览卡**：渠道列表、渠道详情、找不到 | 「返回列表」「返回目录」 | 看完一条渠道，下一步是往回走 |
| **结果卡**：登记成功、查询结果、出错 | 整个主菜单（`cards.with_menu`） | 做完一件事，下一步是重开一件事 |

表单卡给一个「返回目录」当退路 —— 按错了进来、看一眼不想填了得走得掉。但只给退路，
不给整个菜单：表单有自己的提交按钮，底下再堆五个入口只会让人点错。那个按钮必须放在
表单容器**外面**，掉进去它就变成表单动作，必填项没填就退不出去。

「已提交」回执什么按钮都不给，它的下一步是等结果。鉴权失败只回一句红色 toast：名册里
没有的人拿到一排按钮，点了还是同一句拒绝。

### 表格：结果卡里的数排成表

详情卡和佣金查询结果用飞书原生的表格组件（`cards._table`），形状照抄 SDK 自己的
`lark_oapi.channel.card.CardBuilder.table()`，只多一个 `row_height: auto`（默认单行，
长公司名会被截掉）。平台限制：**一张卡最多 5 个表格、一页最多 10 行**（超出的行在表格
里自己翻页，不走回调）。佣金结果一张表最多 120 行，再多就截断并说明 —— 整张卡的 JSON
有大小上限，超了整条消息发不出去。

表格是这套卡片里最新的组件，线下只能照文档和 SDK 对。**万一真机上不收**，发送那一步
会把同样的内容换成列点（`cards.flatten_tables`）再发一次，日志里留下平台回的错误码
（`handlers._send_card`）—— 人照样看得到数，照着错误码改就是。

### 佣金查询：近三个月，只给结果（2026-09-24 反馈）

- 下拉列本月往回 12 个月，预选本月（以前为了预选扫一遍上万行的看板，太慢）
- 查的是**选中这个月和前两个月**，看板只扫一遍
- 结果卡两张表：「每月合计」（月份 | 应付 | 渠道 | 客户），和「每个渠道、每个客户」
  （每个月一列，本月标「至今」）
- **不显示 UID**（太乱，后台照样按 UID 对），**不写「收入 × 比例」的计算过程**，
  「未登记归属的 UID」那一段删了。未登记归属的客户由对账任务照常报（见 jobs/reconcile.py）

### 打开会话就自动弹菜单

订阅 `im.chat.access_event.bot_p2p_chat_entered_v1`（用户进入与机器人的会话），
收到就把主菜单推过去 —— 连第一句话都不用打。

**要去开发者后台单独订阅这个事件**（事件订阅 → 添加事件 → 「用户进入与机器人的会话」）。
没订阅的话代码里注册了也永远收不到，机器人其余功能不受影响。

这个事件**开得很勤**：切回会话、手机上划一下都可能触发。每触发一次就推一张卡的话，
会话很快被菜单卡填满，刚点开的表单会被顶到上面去。所以按人设了 5 分钟冷却期
（`GREET_COOLDOWN_SECONDS`）。

名册里没有的人不推，只留一行 INFO 日志给管理员登记新人 —— 不请自来的一张拒绝卡
对他没有任何用处，而他一旦发消息，现有那条路照样会告诉他。

在结果卡上用整个菜单而不是一个「返回目录」，是为了少一次点击：登记完渠道接着登记客户，
一下就到，不用往上翻。反过来，在导览卡底下再堆五个入口只会让人点错。

### 身份与归属：两条铁律

```
open_id 只从回调的 operator.open_id 取          ← 平台签发，客户端伪造不了
凡是按归属取数据的地方都走 owned_records()      ← 列渠道、挂客户共用同一个过滤器
```

卡片上**没有**「归属销售」这类输入项，`ReferralInput` / `ClientInput` 也不接受它 ——
归属由 open_id 决定。谁能用机器人，取决于销售名册（Sales Directory）里有没有他的
OpenID；名册里没有的人一律被拒，不是默默放行。

归属为空的记录，普通销售看不到（只有管理员能碰）。这是有意的：历史数据在补归属之前
不该人人可见。

### 登记一条渠道时，服务端做了什么

```
校验（名称非空 / 邮箱含 @ / 比例 0-100 / 频率只能是 Monthly 或 Quarterly）
  → 写审计（Audit Log 一行：谁、什么时候、写了什么）
  → 进写锁 → 取编号（读当前最大号 +1）→ 建记录
  → 回读拿到编号（编号列若为自动编号字段，Write 时写不进去，必须回读）
  → 后台线程回填主字段成「R001 ABC Capital」（列表里不再显示 untitled record）
```

编号策略见 `domain/referral.py`：默认后端串行递增（`REFERRAL_AUTO_NUMBER=false`），
改成 Bitable 原生自动编号字段时把它设成 true。

### 为什么几乎所有动作都在后台跑

飞书卡片回调必须在 **3 秒内**返回，否则客户端弹「延时未响应」（本地文案，改不掉）。
以前是按路径挑：登记渠道同步、登记客户和佣金查询异步。现在既然内容都作为新消息推，
就一律在后台跑，回调里只剩「校验 + 回一个响应」：

- 登记渠道 / 客户：格式校验在回调里（填错回 toast），写入在后台，结果推新消息；
- 我的渠道、渠道详情、两个查询：全在后台，算完推新消息；
- 唯一同步的读是翻页：一张一百来行的渠道表，一个请求。

超时不会导致重复提交或丢数据，只会让结果晚几秒到。

## 二、闭环链路

```
 销售在 Lark 里点卡片
        │  （open_id 由平台签发）
        ▼
  机器人 ──写──► Base: Referral Information（渠道）/ Referred Client（客户）
        │                    │
        │                    │  「客户」这一列是登记时写好的单向关联
        ▼                    ▼
  佣金查询 ◄── 看板算式 ── Daily Revenue Board（每日导入的交易明细）
                    │       渠道编号 / 渠道名称 / 分佣比例 / 本笔佣金 全靠关联反查
                    ▼
             reconcile ──► Commission Summary（月度应付，后端算）
```

关键点：**机器人只登记「归属」，一分钱都不算**。算钱在 Base 的公式里
（`本笔佣金 = 总收入(opt+现货+合约) × 分佣比例 / 100`），月度汇总在对账任务里。这样
「钱怎么算」只有一个地方能改，且被测试覆盖。

## 三、闭环还缺什么（2026-09-18 实测）

### 🔴 1. 名册里 OpenID 全是空的 —— 机器人现在谁都进不来

```
Jackie Cao / James YANG / Prance Wang / Kevin Yu    4 人   有 OpenID 的：0
```

`SalesDirectory.require()` 对名册里没有的 open_id 一律拒绝，所以现在**任何人发消息
都只会收到「你还没有被登记为销售」**。这是硬阻塞，必须先解决。

**怎么拿到 OpenID**（两种都行）：

```bash
# ① 跑一次冒烟脚本，点一下卡片，日志里会打印 open_id
uv run python scripts/ws_smoke.py

# ② 让本人给机器人发一条消息 —— 服务端会记一条 warning：
#    「未登记的 open_id 尝试操作: ou_xxx」  从日志里抄出来
```

拿到之后填进名册的 OpenID 列即可（也可以由管理员在 Base 界面直接填）。

### 🔴 2. 存量 101 条渠道没有归属人 —— 即使 OpenID 填好，销售也看不到自己的渠道

模板导入时有意留空了（模板里只有姓名，没有 OpenID），见
`scripts/import_registrations.py` 的「归属人先空着」。实测：

```
Referral Information  101 条   有『登记人OpenID』的：0
```

后果：`owned_records()` 过滤后普通销售**看不到任何渠道**，于是「登记新客户」的
渠道下拉是空的、「我的渠道」也是空的。机器人登记的新渠道不受影响（写着归属）。

**补法**：按「负责销售」这一列的姓名去名册对 OpenID，回填 `归属销售`（人员）+
`登记人OpenID`（文本）两列。姓名对不上的（同名/改过名）单独列出来人工确认。
这是一个一次性脚本能做完的事，建议放在 OpenID 填好之后跑。

### 🟡 3. 一个渠道只能有一个归属人 —— 「多 openid」还没实现

现在的形状是「一条渠道 = 一个 open_id」：

```
归属销售 (人员，可多人)      ← 实际只写了一个
登记人OpenID (文本)          ← 归属过滤读的是这一列，只有一个值
```

要支持一个渠道挂多个 open_id（多个对接人/多个销售共同维护），需要改三处：

1. 登记表单加一个「其他对接人」的多选人员组件（或让管理员在 Base 里加人）；
2. `owned_records()` 从「相等」改成「在列表里」—— 文本列可以存多行，也可以改读
   人员字段；
3. 回填脚本要能写多个值。

**这一步需要先明确语义**（见下面的待确认问题），再动代码：到底是「一个渠道有多个
对接人都能登记客户」，还是「多个销售共同拥有这个渠道的佣金归属」？两者的权限模型
不一样。

### 🟡 4. 登记客户时不知道 UID 是不是打错了

现在只查「这个 UID 有没有被登记过」，不检查它是否真实存在。今天的数据诊断里就有
**54 个已登记客户的 UID 在交易明细里查无此人**（`/tmp/unmatched_clients.csv`）——
如果是打错一位，这个渠道永远算不出佣金，而且没有任何提示。

可行的做法：登记时拿 UID 去**看板的 UID 集合**（或当天工作簿）里查一次，查不到就
提示「这个 UID 在近期交易明细里没出现过，请核对」。不拦，只警告。

### ✅ 5. 机器人已经常驻（「进程不在」和「连接断了」是两件事）

**现状**（2026-09-22）：`scripts/install-bot-launchd.sh` 把它装成了 launchd 任务，
`RunAtLoad` + `KeepAlive` —— 开机自启，崩溃自动拉起。

**但那只解决「进程不在」。长连接断了一直都是 SDK 自己接回来的**：重连是**无限次**的
（源码 `while True` + 每次间隔 120 秒带随机抖动），下面这段实测记录说明的就是这件事，
和装不装 launchd 无关：

| 时间 | 事件 | 空窗 |
|---|---|---|
| 09-18 23:36 | 连接建立 | — |
| 09-19 07:30 → 15:44 | 断线；三次重连全失败（DNS 解析不了 `open.feishu.cn`） | **8 小时 14 分** |
| 09-19 15:59 → 15:59:36 | 断线 → 重连成功 | 25 秒 |
| 09-19 15:59 → 09-20 10:40 | 稳定 | 16 小时 41 分 |
| 09-20 10:40 → 10:42 | `keepalive ping timeout` → 重连成功 | **1 分 55 秒** |

两条结论（分清「进程不在」和「连接断」）：

1. **要防的是「进程不在」**：崩溃、重启机器之后没人把它拉起来 —— 这正是 KeepAlive
   管的事，`scripts/com.chao.crm-basebot.bot.plist.template` 已经装上了。连接本身会自愈。
   ⚠️ 装的是**用户级**（`gui/$(id -u)`）任务：那个账号登出、或机器重启后停在登录界面，
   它不会自己起来。要真 7×24 得开自动登录或改成系统级 LaunchDaemon，两者都要管理员密码。
2. **短暂空窗是这类网络环境的固有代价**：心跳间隔 120 秒是**服务端配置**
   （`client.py:452`，`conf.PingInterval`），客户端改不了 —— 网络消失后最多两分钟才被发现，
   再等一次重连间隔。笔记本休眠 / VPN 切换 / 换 Wi-Fi 都会造成这种窗口。
   要真正 7×24，得把它放在**常开的机器**上（小服务器 / VPS），笔记本做不到。
   ⚠️ **空窗期的消息不补发**：对方看到的是「机器人没反应」，不会收到任何错误。

**「断线可见」已经有了**：`scripts/bot_connectivity_report.py` 把日志读成时间线，只报超过阈值的
空窗（默认 1 分钟；秒级抖动自动忽略）：

```bash
uv run python scripts/bot_connectivity_report.py --log logs/bot.log
#   连接记录 11 条 · 断开 5 次 · 累计空窗 8.3 小时 · 最长 8.2 小时
#   ⚠️ 有 3 段空窗超过 1.0 分钟（这些窗口里的消息不补发）：
#     2026-09-19 07:30:38 → 2026-09-19 15:44:53   空窗 8.2 小时
#     2026-09-20 10:40:08 → 2026-09-20 10:42:03   空窗 1.9 分钟
#     2026-09-20 21:40:10 → 2026-09-20 21:41:47   空窗 1.6 分钟
```

**退出码**：有空窗超阈值 = 1，否则 0 —— 挂进 cron / launchd 就是「有事才通知」，
一切正常时无声无息（日志得先落到文件，见 `docs/PIPELINE.md` 的 launchd 写法）。
